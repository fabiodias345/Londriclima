# Refresh token sem detecção de reutilização

**ID:** vuln-0002  
**Severidade:** MÉDIA  
**Alvo:** `http://host.docker.internal:3000`  
**Endpoint:** `/api/v1/auth/refresh`  
**Método:** POST  
**CWE:** CWE-613  
**CVSS:** 4.3  
**Esforço de correção:** Médio

## Descrição

O endpoint emite um novo par de tokens a cada uso, mas não invalida o refresh token já consumido. O mesmo token capturado pode ser reapresentado repetidamente durante sua validade de 30 dias.

## Evidência

```text
uso #1 -> 201 (novo refresh emitido)
uso #2, com o mesmo token original -> 201 (novo refresh emitido)
```

Tokens de acesso enviados ao endpoint de refresh são rejeitados, e tokens `alg=none` também são rejeitados. O problema específico é a ausência de rotação com detecção de reutilização.

## Impacto

Como refresh tokens são credenciais Bearer de longa duração armazenadas em `localStorage`, um token capturado pode ser reutilizado para emitir novos access tokens sem detecção ou revogação no servidor. No sandbox, o impacto limita-se às contas de teste; em produção, permitiria persistência de acesso não detectada.

## Prova de conceito

1. Fazer login e obter um `refresh_token`.
2. Enviar `POST /api/v1/auth/refresh` com esse token; a API retorna `201`.
3. Reenviar exatamente o mesmo token original; a API retorna `201` novamente.
4. Repetir até a expiração do token.

## Correção

Persistir um hash do refresh token, registrar sua família e invalidar o token após o uso. Se um token já usado for reapresentado, revogar toda a família e exigir novo login. Associar tokens a uma sessão de servidor para permitir revogação em logout e troca de senha. Considerar cookies `HttpOnly`/`Secure` e menor tempo de expiração.

## Premissas

O atacante precisa obter previamente o refresh token. O achado é uma falha de defesa em profundidade de gerenciamento de sessão, não uma exploração remota isolada.
