# Upload irrestrito de arquivo no endpoint de foto do técnico

**ID:** vuln-0001  
**Severidade:** BAIXA  
**Alvo:** `http://host.docker.internal:3000/api/v1/admin/tecnicos/{tecnicoId}/foto`  
**Método:** PATCH  
**CWE:** CWE-434  
**CVSS:** 2.7  
**Esforço de correção:** Médio

## Descrição

O endpoint aceita qualquer conteúdo como “foto”, sem validar tipo, extensão, magic bytes ou tamanho. Arquivos de texto e binários são armazenados, e a extensão é derivada do nome enviado pelo cliente.

## Evidência

```text
# Texto enviado com filename=foto.jpg
HTTP/1.1 200 OK
{"foto_perfil_storage_url":"/storage/funcionarios/.../perfil/foto.jpg"}

# Binário de 2 MB enviado com filename=big.png
HTTP/1.1 200 OK
{"foto_perfil_storage_url":".../perfil/foto.png"}

# Sem token
HTTP/1.1 401 {"message":"Token de acesso ausente."}
```

O caminho gerado não foi servido de volta neste ambiente (`404`), portanto o impacto demonstrado limita-se à integridade do arquivo armazenado. Se o storage for servido inline em produção, pode haver XSS armazenado, injeção HTML ou spoofing.

## Prova de conceito

1. Obter um Bearer token administrativo.
2. Enviar `probe.txt` contendo `hello not an image` como campo multipart `foto`, declarando `image/jpeg` e filename `foto.jpg`.
3. Observar resposta `HTTP 200` e a URL de armazenamento.
4. Repetir com binário de 2 MB e filename `big.png`; a extensão armazenada muda para `.png`.

## Correção

Decodificar e validar a imagem no servidor, rejeitar magic bytes inválidos, limitar tamanho, usar MIME/extensões permitidos independentemente do nome do cliente, reprocessar para JPEG/PNG seguro e gerar o nome do arquivo no servidor. Servir com `Content-Type` explícito e `X-Content-Type-Options: nosniff`.

## Premissas

É necessário usuário autenticado. O arquivo não é servido inline neste sandbox; o impacto de XSS só existiria se o storage fosse publicado dessa forma em produção.
